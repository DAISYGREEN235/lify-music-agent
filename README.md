# Lify（ListenForYou）音乐推荐智能体

> 由我所想，听我想听。


## 一、项目说明
### Lify 音乐推荐智能体｜Agent 架构与任务编排（个人项目）

面向用户自建歌单中“收藏歌曲难筛选、场景需求难落实”的问题，开发对话式音乐策划原型，将场景、期望情绪与音乐文字偏好转化为结构化需求，结合曲库检索、约束校验与歌单编排，支持多轮修改、可解释选歌及中断恢复；完成融合音频特征、歌词语义和用户偏好的扩展架构设计，探索“由我所想，听我想听”的个性化音乐体验。

- **Agent 架构与任务编排：**基于 LangGraph StateGraph 构建“意图解析—计划—工具选择—执行—校验—有界修复”状态流程，通过条件路由处理澄清、异常和候选不足；按阶段暴露合法工具，配合调用预算与执行步数上限约束异常循环。
- **工具调用与业务约束：**封装曲库检索和歌单编排工具，采用 Tool Calling 与执行侧校验，限制调用顺序、工具名称及参数；对曲目 ID、目录事实、排除条件和总时长进行复核，候选不足时返回部分结果或不足状态，避免虚构歌曲与擅自放宽限制。
- **上下文管理与会话恢复：**基于 SQLite Checkpointer 持久化状态，通过用户与会话联合标识隔离任务，支持暂停恢复及多轮局部修改；采用结构化需求、最近错误与历史摘要裁剪控制模型上下文，保留已确认条件。
- **检索与歌单编排：**实现标签匹配、可选文本向量检索及硬条件过滤，在时长上限内按歌曲数量与匹配分选择候选，支持相关性排序和演示能量标签排序，输出可追溯的选曲与排序理由。
- **异常恢复与回归评测：**建立覆盖正常策划、多轮修改、工具故障及会话约束的 20 道任务评测并保存逐题轨迹；针对重复检索问题引入阶段工具约束，在同组 8 道真实模型结构化输入开发样例中，将任务标准通过数由 3/8 提升至 8/8，另完成 8 道真实模型保留样例与 15 次重复检查。

**技术栈：**Python、LangGraph、SQLite Checkpointer、Tool Calling、文本 Embedding、JSON Schema、自动化任务评测。

上述量化结果来自仓库内 2026-09-29 的评测记录，属于小样本受控任务验证；任务通过包含正确返回不足或停止，不等同于歌单生成成功率，也不代表听感准确率。

## 二、整体设计思路

### 2.1 产品定位

Lify 面向用户已有曲库，通过自然语言理解当下需求，在可用歌曲中完成选择、排序、解释和修改，目前使用音乐规模1800首。

设计分为三个职责层：

1. **交互与意图层：**理解场景、目标情绪、音乐偏好、时长及否定条件，将多轮输入更新为结构化需求。
2. **检索与决策层：**从曲库获取候选，执行硬约束过滤、相关性排序、多样性控制和歌单编排。
3. **执行保障层：**维护会话状态、检查工具调用、校验结果、限制修复次数，并记录可回放的执行轨迹。

模型负责理解和工具选择；程序负责歌曲事实、业务规则、时长计算与结果校验。推荐解释必须能追溯到曲库记录、标签或计算结果。

### 2.2 用户体验

- **场景选歌：**“通勤时想放松一点，旋律舒缓，选 3 首，总时长不超过 20 分钟。”
- **多轮修改：**“改成 2 首，保留刚才的场景，不要这个歌手。”
- **可解释输出：**显示曲目来源、总时长、选曲理由及排序依据。
- **相似歌曲推荐（扩展设计）：**选择一首种子歌，再描述“保持氛围，但更轻快”。
- **歌单编辑（扩展设计）：**替换、删除、保留及重新排序指定曲目，编辑后重新执行全量约束校验。

当前支持文字偏好策划与多轮条件更新；原始音频理解、种子歌曲声学检索、直接播放及持久化歌单编辑属于扩展范围。

### 2.3 架构与部署

采用模块化单体：交互入口、状态图、检索排序与歌单编排在同一应用中组织，音频特征在离线流程生成。目标曲库规模下先验证数据与推荐质量，再根据实测决定是否拆分服务。

```text
用户输入 / 多轮修改 / 种子歌曲（扩展）
                  ↓
          结构化意图与约束合并
                  ↓
       LangGraph 有状态任务编排
                  ↓
       工具选择 → 检索 → 组单
                  ↓
         事实与业务约束校验
          ├─ 合法：返回歌单及理由
          ├─ 不足：返回状态，等待用户调整
          ├─ 可修复：限定次数后重试
          └─ 不可恢复：停止并说明原因

当前数据：JSON 曲库 + 可选文本向量缓存 + SQLite 检查点
扩展数据：PostgreSQL / pgvector + 音频文件 + 用户偏好
观测数据：当前本地轨迹与评测文件；扩展接入 OpenTelemetry
```

## 三、核心内容

### 3.1 状态图与任务编排

状态图由 `parse → plan → choose → execute → check → finish` 构成，工具选择或执行发生可恢复错误时进入 `reflect`，最多进行一次修复。业务计划为预设流程，模型在受控工具集合中选择动作。

- 状态包含当前需求、候选歌曲、歌单结果、执行阶段、错误、修复计数、调用计数与历史摘要。
- 默认动作选择预算为 4 次，可配置范围为 0–6；图执行设置 `recursion_limit=40`。
- 未检索时只暴露 `search_catalog`，已有候选后只暴露 `compose_playlist`；空候选也必须进入组单以形成明确不足状态。
- 参数不完整或不支持的需求进入澄清；结果事实或硬约束校验失败时停止，避免携带错误结果继续输出。
- 执行前后核对曲库摘要，发现目录变化时要求重新发起请求，避免使用过期候选。

### 3.2 工具调用与数据契约

当前以结构化 `needs` 字典传递需求，使用 JSON Schema 描述工具接口，并由 Python 校验业务字段。工具调用采用空参数对象，实际需求由已确认的状态传入，避免模型在工具调用时再次改写用户约束。

已实现字段包括：

- `scene`、`mood`、`current_mood`、`melody`：场景、期望情绪、当前情绪及音乐文字偏好。
- `count`、`max_minutes`：目标歌曲数量与总时长上限。
- `exclude_artists`、`exclude_songs`：明确排除项。
- `language`、`vocal`：语言与人声限制。
- `order`：相关性、能量渐强或能量渐弱排序。

其中 `melody` 当前表示文字偏好与演示标签匹配，不代表主旋律提取。Pydantic `MusicIntent` 属于下一版本的数据契约升级，当前没有相应业务模型实现。

### 3.3 会话状态与上下文管理

使用 `SqliteSaver` 保存图状态，以用户和会话标识组合生成检查点命名空间，支持工具执行后暂停及恢复。该隔离机制不等于登录鉴权，部署时应由服务端认证身份提供用户标识。

多轮更新采用“已有需求 + 本轮补丁”的方式，未修改字段继续保留，明确取消条件时才清空。模型只接收确认需求、当前阶段与最近错误；历史摘要保留最近 3 轮，节点轨迹保留最近 40 条，用量状态保留最近 20 条。

当前摘要是程序生成的结构化结果摘要，尚未实现长期用户偏好存储、自动记忆归纳或完整的跨会话偏好学习。

### 3.4 检索、编排与解释

当前检索以场景、情绪与音乐文字标签匹配计分；可选语义入口使用文本 Embedding 比较用户需求与曲目描述，并缓存向量。此处文本来自曲目元数据与演示标注，不是从真实音频或完整歌词提取的多模态表示。默认状态图检索尚未接入该可选语义分支。

硬约束在检索与最终校验两处执行：明确排除的歌曲或艺人不得出现；未知语言、人声属性不得视为满足明确限制；设置时长上限时排除时长未知的歌曲。

组单先最大化可满足的歌曲数量，再最大化匹配分，随后按相关性或演示能量标签排序。时长是上限，不承诺精确凑满。当前组合搜索限定目录最多 20 首，扩展至 1,800 首前必须替换选择算法。

选曲理由来自命中标签或语义候选状态；排序理由来自实际排序规则。当前标签尚待试听复核，因此不能据此宣称真实音乐情绪或旋律判断准确。

### 3.5 Agent Harness 与异常恢复

Harness 指围绕模型执行的约束、校验、恢复与记录机制，当前包括：

- 校验工具名称、调用数量、空参数对象和执行顺序。
- 对工具选择与执行失败进行一次有界修复，持续失败后停止。
- 对目录事实、重复 ID、数量、排除项与总时长进行最终检查。
- 候选不足返回 `partial` 或 `insufficient`，不补造歌曲、不自动修改硬条件。
- 模型接口设置超时；预算耗尽返回 `budget_exhausted`。

当前未实现指数退避、持久化写操作的幂等控制或端到端恰好执行一次保证。工具恢复与网络层重试需要分别设计，避免叠加重试造成额外调用。

## 四、多模态与个性化扩展设计

本节为已形成的设计方案，不作为当前已交付能力或实测成果表述。

### 4.1 统一意图与类型化工具

设计 Pydantic `MusicIntent`，统一表达场景、情绪、种子曲 ID、语言、人声、时长、偏好与排除项，并为每项区分硬约束和软偏好。保留约束来源、作用范围及本轮修改信息，避免把模型推断当成用户明确要求。

工具扩展为曲库查询、相似曲检索、歌单生成及歌单编辑。服务端提供可信用户身份；工具执行前检查曲目归属和可播放状态，参数类型检查不能替代业务权限与数据有效性检查。

### 4.2 歌曲画像与多路召回

为每首歌建立统一 ID、基础元数据、可用状态、音频特征、歌词语义、场景标签与特征版本。自动标签记录来源、置信度和审核状态；缺失特征保留为空，不填入模型猜测值。

- **音频路：**离线提取音频向量、BPM 与可解释的能量特征，用于种子曲听感推荐。
- **歌词路：**由实际歌词提取主题、情绪与文本向量，区分歌词表达和音乐听感。
- **标签路：**使用受控情绪、场景、人声及语言标签，支持筛选与冷启动。
- **偏好路：**根据明确反馈及近期播放记录调整得分，初期使用规则，不依赖稀疏数据训练复杂模型。

向量采用 PostgreSQL + pgvector 存储，先建立精确检索基线。不同模型的音频向量和文本向量分别检索，再融合结果；只有配套训练的跨模态编码器才能进行对应空间的文本—音频比较。

### 4.3 RRF 融合、MMR 选择与歌单排序

各路召回先按可判断的硬条件筛选，再通过加权 RRF 融合排名：

```text
RRF(track) = Σ route_weight / (k + rank_route(track))
```

仅对该路实际召回的歌曲计分，`k` 与路权重通过开发集选择；缺失音频或歌词时跳过对应分支。RRF 用于合并不同来源的排名，不直接混加尺度不同的向量分数。

之后结合场景匹配、偏好和近期重复情况重排，通过 MMR 在相关性与候选间冗余之间做取舍。MMR 的相关性与相似度应统一量纲，并明确定义用于比较歌曲的特征空间。

歌单编排单独处理总时长、同艺人间隔、已保留曲目、能量变化和相邻曲过渡。对 1,800 首目标曲库先缩小候选集，再采用有界搜索或动态规划选择组合，避免沿用全目录穷举。MMR 不能代替时长约束，也不能单独保证播放连续性。

### 4.4 分层记忆与可编辑歌单

- **会话记忆：**当前意图、已选歌曲、临时排除项与最近修改，由 Checkpointer 管理。
- **长期偏好：**独立存储用户明确表达的稳定喜好和不再推荐项，记录来源与更新时间，支持撤销。
- **场景偏好：**“工作时少人声”只影响对应场景，不自动转为所有场景的全局限制。

一次跳过只作为弱反馈；“现在不想听”写入会话条件，“以后不要推荐”才进入持久排除项。歌单编辑采用版本号与幂等键，替换或删除后重新校验全部约束，防止重复写入和并发覆盖。

### 4.5 恢复与观测升级

将错误标准化为参数错误、候选不足、瞬时故障、事实冲突及预算耗尽等类型。参数错误提供结构化反馈；瞬时故障采用有上限的退避重试；候选不足仅向用户提出可调整项，未获得新指令前保持原有硬条件。

规划接入 OpenTelemetry，以请求为根链路追踪意图解析、模型调用、检索、排序、校验与编辑，记录耗时、调用次数、错误类型和供应商返回的 Token 用量。失败调用与修复调用均应计入任务成本；先解决现有用量遗漏，再计算成本指标。

## 五、评测依据与效果边界


- **任务标准通过率：**按用例预期结果计算，明确区分生成成功、正确不足、正确澄清及失败。
- **硬约束满足率：**统计返回歌单是否满足全部硬约束；空结果单列，避免靠不返回歌曲提高指标。
- **nDCG@K：**在人工听评形成分级相关性标注后评估排序，不能用模型自产标签充当真实金标准。
- **歌单体验：**通过试听评价场景适配、多样性及过渡自然度，不能仅凭 BPM 接近判定连续性良好。
- **P95 延迟：**固定任务口径、模型配置与运行环境，分别报告样本量、单轮及多轮任务延迟。
- **单次成功任务成本：**同批全部尝试的已确认调用费用除以成功完成任务数，计入失败与修复开销；缺少价格或用量时标记未知。

Prompt、工具描述、检索权重、模型与曲库版本均应随评测记录保存。在开发集分析失败、修改单一因素后，再使用保留集回归，避免将工具调用成功率当成用户任务完成率。
