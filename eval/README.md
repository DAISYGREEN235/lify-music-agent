# V1.0 评测边界与操作

`scenarios.json`是场景验收输入，不是已经通过听感验证的标签集。

先执行自动测试，验证约束、预算和恢复的程序行为；再用真实API生成场景歌单，按以下步骤试听：

1. 固定曲库指纹、模型版本、场景文本及候选池，保存歌曲ID。
2. 对同一池内每首歌按“适合当前场景”评分0/1/2：不适合、部分适合、适合。全局喜欢与场景适配分开。
3. 候选池必须明确；前K缺标签不计算 Precision/NDCG，把未评歌曲当负例会制造假精度。Recall仅针对已标注固定池，不能宣称全曲库召回。
4. 比较音频单路、歌词单路和融合时，保持相同评测输入，记录失败例子与负向条件误判。
5. 真实播放指标检查原始事件来源与采集缺口。点击播放、进入文件、自然EOF、覆盖80%、主动早跳是不同事件。

当前命令`lify evaluate`提供真实事件计数；完整满意度、收藏、分享、跨日留存需对应事件和足够样本，不应仅凭接上播放器就输出这些比率。

标签函数示例（示例数据，不是项目效果）：

```python
from lify.evaluation import ranking_metrics
ranking_metrics(['id-a', 'id-b'], {'id-a': 2, 'id-b': 0, 'id-c': 1}, k=2)
```

场景适配对不同用户主观性强。首轮由项目使用者试听，不将LLM自行评价当作真实用户标签。
